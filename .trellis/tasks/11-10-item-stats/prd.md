# 11-10-item-stats（我的商品：浏览量 / 想要量）

## Goal

让用户在「商品管理」里直接看到**每个自己商品**的浏览量、想要量，用于观察哪些商品更受关注；
数据按需抓取、有缓存，不违反项目防风控铁律。

## 背景与已确认事实（实测取证）

- 唯一可靠来源是**商品详情接口**（`mtop.taobao.idle.pc.detail`）。对本店商品 `1098309932961` 实测返回：
  ```
  itemDO.browseCnt  = 22   （浏览量）
  itemDO.wantCnt    = 2    （想要量，wantCntUnit = "人想要"）
  itemDO.collectCnt = 1    （收藏）
  itemDO.soldCnt    = 0    （已售）
  ```
- 自有商品**列表卡片**（`mtop.idle.web.xyh.item.list`）里**只有「N人想要」文本标签、没有浏览量**：
  对库内 36 个商品统计，明细中出现「浏览」字样的为 **0** 条。故浏览量必须取自商品详情接口。
- 商品详情接口在**服务器侧浏览器会被平台确定性判罚**，已通过**本机抓取助手**（真实 Chrome + 反向隧道）打通，
  单次约 2–4 秒；助手不可用时接口返回 `503 local_fetch_unavailable`（现有行为，本次复用）。

## Requirements

- R1 列表展示：在「商品管理」列表「价格」列之后新增**「浏览」「想要」两列**。
- R2 悬浮详情：鼠标悬浮在这两列上时显示「收藏 N · 已售 N · 更新于 X 前」；无数据时两列显示「—」。
- R3 单个刷新：每行提供「刷新数据」按钮，只抓该商品一次并落库。
- R4 批量刷新：工具栏提供「刷新本页」按钮，作用于**当前列表页**的商品：
  - 只挑**未抓过或已超过缓存有效期**的商品，**最旧优先**；
  - **单轮上限 10 个**，**严格串行**执行；
  - **遇到风控（`RGV587` / `FAIL_SYS_USER_VALIDATE`）立即停止**本轮，已抓到的结果保留；
  - 返回值包含「本轮已刷新数量」与「剩余待刷新数量」，便于反复点击补齐。
- R5 缓存：有效期 **24 小时**；缓存内直接返回，不触发助手请求；**手动刷新（单个或批量）强制重新抓取**。
- R6 数据范围：与列表一致，包含已下架商品（`status = down`）；数据按 `(cookie_id, item_id)` 归属账号与商品。
- R7 失败语义：
  - 助手不可用 / 未登录 → `503 local_fetch_unavailable` / `local_fetch_not_logged_in`（复用现有错误与文案）；
  - 平台要求人机验证 → `409 local_fetch_risk_control`；
  - **不做服务器侧浏览器回退**（该路径已被判罚，回退只会浪费时间并加重风控）。

## Acceptance Criteria

- [ ] 列表显示「浏览」「想要」两列；有数据显示数字，无数据显示「—」。
- [ ] 悬浮显示「收藏 N · 已售 N · 更新于 X 前」；无数据时不显示悬浮内容。
- [ ] 单个刷新：调用后该商品数据落库并在列表中更新（端到端实测）。
- [ ] 批量刷新：单轮最多 10 个；24 小时内已新鲜的商品被跳过；串行执行；
      遇风控立即停止并保留已抓结果（有测试证明）。
- [ ] 命中 24 小时缓存时不向助手发起请求（有测试证明）。
- [ ] 助手离线时返回 503 + 可操作提示，且**不触发**服务器侧浏览器（有测试证明）。
- [ ] 三方言迁移同号（64）、最终表结构一致；`item_stats` 以 `(cookie_id, item_id)` 唯一。
- [ ] 门禁：`go test ./...`、架构门禁、`commentlint`（前后端）、`make api-check`、前端 typecheck 全通过；
      Go 覆盖率不低于 90%；前端新增逻辑有行为测试。
- [ ] `api/openapi.yaml` 新增两个端点并补充契约测试与成功契约场景。

## 术语

- **商品浏览/想要**：闲鱼商品详情中的浏览量（`browseCnt`）与想要量（`wantCnt`）。
- **数据新鲜度**：`item_stats.fetched_at` 与当前时间之差；超过缓存有效期即为过期。
- **单轮批量刷新**：一次用户点击触发的、有硬上限的串行抓取批次。
